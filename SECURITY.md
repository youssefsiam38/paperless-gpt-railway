# Security

## Reporting

Open an issue at https://github.com/youssefsiam38/paperless-gpt-railway/issues for a problem with
the wrapper. Report anything in the application itself to https://github.com/icereed/paperless-gpt.
Do not include credentials, tokens or public hostnames in an issue.

## The central fact

paperless-gpt has no authentication. From `main.go`:

```go
api.GET("/documents", app.documentsHandler)
api.POST("/generate-suggestions", app.generateSuggestionsHandler)
api.POST("/settings", app.updateSettingsHandler)
api.POST("/documents/:id/ocr", app.submitOCRJobHandler)
```

About thirty routes, none of them checking a credential, and no setting that adds one. The project
is built to run on a private network beside the paperless-ngx it talks to.

Deployed unmodified to a platform that assigns a public hostname, the result is worse than an open
application, because of what it is holding the keys to:

- it can **read every document** in the connected archive, which for most people means contracts,
  invoices, payslips and correspondence;
- it can **rewrite their titles, tags, correspondents and document types**;
- it can **send page images to a language model** on the API key you configured, which is both a
  disclosure and a bill.

This template exists to close that.

## What is exposed

| Route | Anonymous | Authenticated |
|---|---|---|
| `/healthz` | 200, the word `ok` | same |
| `/` | 401 | the web interface |
| `/api/**` | 401 | the API, and through it the archive |

`/healthz` is the wrapper's own route. It does not proxy to the application and never touches the
archive, so the platform can probe the service without holding a credential and without a route
existing that reaches your documents.

## Deliberately opting out

`PAPERLESS_GPT_ALLOW_PUBLIC=true` removes authentication completely. The container then logs a
warning on every start. Set it only when the instance is on a private network or behind another
gateway that authenticates for you. On a public Railway domain it means anyone who finds the URL can
read and rewrite your archive.

## Secrets

- `PAPERLESS_GPT_AUTH_PASSWORD` is generated by the template with `${{secret(24)}}` and is never
  printed by the wrapper. The start-up log reports the username and the password's length.
- The password is hashed with `caddy hash-password` before it reaches disk. The generated Caddy
  configuration holds only the bcrypt hash, is written `0600`, and is regenerated on every start
  rather than persisted.
- `PAPERLESS_API_TOKEN` is passed straight to the application. The start-up log reports its length,
  never its value, and a test asserts that.
- Model-provider keys such as `OPENAI_API_KEY` are passed straight through and are not logged.
- Nothing is baked into the image at build time. There are no credentials in the Dockerfile, in a
  build argument, or in any layer, and static checks assert it for each one.

## The token you give it

The paperless-ngx API token this service uses carries the permissions of the user it belongs to. If
you want to limit what a compromise of this instance could do, create a dedicated paperless-ngx user
with only the document permissions paperless-gpt needs and take the token from that account rather
than from your own.

## Rotating credentials

- The basic-auth password: change `PAPERLESS_GPT_AUTH_PASSWORD` and redeploy. There is no session
  state to invalidate.
- The paperless token: revoke it in paperless-ngx, mint a new one, change `PAPERLESS_API_TOKEN` and
  redeploy.

## Transport

Railway terminates TLS at its edge and the certificate covers the generated domain. Plain HTTP
redirects to HTTPS. Caddy runs with `auto_https off` because it is behind that edge.

Use an `https://` address for `PAPERLESS_BASE_URL` unless the paperless-ngx is on Railway's private
network, where `http://` over the internal domain does not leave the platform. The entrypoint
refuses an address with no scheme at all.

## Data handling

Nothing from the archive is stored here. `/app/db` holds job records and settings. Documents are
fetched per request, and page images are sent to whichever model provider you configured, which is
the one path off the instance and the reason to choose that provider carefully.

## Third-party calls made by the application

Your paperless-ngx, and your language-model provider. Nothing else.

## Updates

The upstream image is pinned by digest. A version bump is a pull request that changes the digest, is
tested by CI against the real image, and is released as a new wrapper tag. See `MAINTENANCE.md`.
